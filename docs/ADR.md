# Architecture Decision Records

## 철학
MVP 최소주의. 최소한의 변경으로 최대 산출. 한 번만 쓰는 추상화, 발생하지 않을 시나리오 대비, 과한 세분화는 만들지 않는다. 작동하는 최소 구현을 선택한다.

---

### ADR-001: Next.js App Router 풀스택
**결정**: 프론트와 API를 하나의 Next.js 15 App Router 앱으로 구성. 별도 백엔드 없음.
**이유**: 단일 페이지 도구라 별도 서버는 과함. 라우트 핸들러 하나로 API 키 보호와 외부 호출을 처리할 수 있다.
**트레이드오프**: 백엔드를 독립 확장/재사용하기는 어려움. MVP 범위에선 불필요.

### ADR-002: 외부 API(gpt-image-2)는 라우트 핸들러 + service에서만 호출
**결정**: OpenAI 호출은 `app/api/generate/route.ts` → `src/services/openai.ts`에서만. 클라이언트 직접 호출 금지.
**이유**: `OPENAI_API_KEY`를 서버에만 두어 노출을 막고, service를 SDK 모킹 가능한 테스트 seam으로 삼는다.
**트레이드오프**: Server Action을 쓰면 라우트·fetch 보일러플레이트를 줄일 수 있으나, 라우트 핸들러가 TDD seam이 더 명확하고 Harness 레이어 분해(서비스/라우트/UI)와 1:1로 맞아 라우트 핸들러를 택함.

### ADR-003: 이미지 영구 저장 안 함
**결정**: 생성 결과(base64 PNG)를 응답으로 바로 브라우저에 반환하고 다운로드는 클라이언트에서 처리. DB/스토리지 미도입.
**이유**: MVP엔 히스토리/공유가 없으므로 저장 인프라가 불필요. 비용·복잡도 절감.
**트레이드오프**: 새로고침/재생성 시 이전 결과 소실. 큰 base64 페이로드를 매번 전송. MVP에선 수용.

### ADR-004: 테스트 러너로 Vitest 채택
**결정**: 단위 테스트는 Vitest로 작성.
**이유**: Next.js/TS와 통합이 간단하고 빠르며, SDK 모킹이 용이. TDD Guard 훅과 함께 lib/services/api 로직을 테스트 우선으로 구현.
**트레이드오프**: Jest 생태계 자료가 더 많지만, 설정 단순성과 속도를 우선.

### ADR-005: 에러는 4버킷으로 정규화
**결정**: OpenAI 예외를 사용자 행동이 갈리는 4개 코드(`INVALID_INPUT`·`MISSING_API_KEY`·`CONTENT_POLICY`·`GENERATION_FAILED`)로만 정규화.
**이유**: 429/타임아웃/네트워크/미상은 사용자에게 동일하게 "재시도" 안내로 귀결 → 세분화 이득 없음. 응답에 원본 에러를 노출하지 않아 정보 누출도 방지.
**트레이드오프**: 세밀한 에러 분석/로깅엔 불리. MVP UX엔 충분.
